# 코드베이스 아키텍처 개선

아키텍처적 마찰을 표면화하고 **심화 기회**를 제안한다 — 얕은 모듈을 깊은 모듈로 바꾸는 리팩터링. 목표는 테스트 가능성과 AI 탐색 가능성이다.

이 스킬은 프로젝트의 도메인 모델에 기반하며 공통 설계 어휘 위에 구축된다:

- 아키텍처 어휘(**module**, **interface**, **depth**, **seam**, **adapter**, **leverage**, **locality**)와 원칙(삭제 테스트, "인터페이스가 테스트 표면", "어댑터 하나 = 가상적 seam, 둘 = 실제")을 위해 `/codebase-design` 스킬을 실행한다. 모든 제안에서 이 용어들을 정확히 사용한다 — "component," "service," "API," "boundary"로 표류하지 않는다.
- `CONTEXT.md`의 도메인 언어가 좋은 seam의 이름을 제공한다; `docs/adr/`의 ADR은 이 스킬이 재논의하지 말아야 할 결정을 기록한다.

## 진행 순서

### 1. 탐색

먼저 프로젝트의 도메인 용어집(`CONTEXT.md`)과 수정하는 영역의 ADR을 읽는다.

그다음 `subagent_type=Explore`로 Agent 도구를 사용해 코드베이스를 탐색한다. 경직된 휴리스틱을 따르지 말고 유기적으로 탐색하며 마찰을 느끼는 곳을 기록한다:

- 하나의 개념을 이해하기 위해 여러 작은 모듈 사이를 오가야 하는 곳은 어디인가?
- 모듈이 **얕은** 곳 — 인터페이스가 구현만큼 복잡한 곳은?
- 테스트 가능성을 위해 순수 함수를 추출했지만, 실제 버그는 그것들이 호출되는 방식에 숨어 있는 곳(**locality** 없음)은?
- 긴밀하게 결합된 모듈이 seam 너머로 새어 나오는 곳은?
- 테스트되지 않거나, 현재 인터페이스를 통해 테스트하기 어려운 코드베이스 부분은?

얕다고 의심되는 것에 **삭제 테스트**를 적용한다: 삭제하면 복잡성이 집중되는가, 아니면 그냥 이동하는가? "예, 집중됩니다"가 원하는 신호다.

### 2. HTML 리포트로 후보 제시

레포에 아무것도 남기지 않도록 OS 임시 디렉토리에 독립적인 HTML 파일을 작성한다. `$TMPDIR`에서 임시 디렉토리를 확인하고, 없으면 `/tmp`(Windows는 `%TEMP%`)로 폴백하고, `<tmpdir>/architecture-review-<timestamp>.html`에 작성해 실행마다 새 파일이 생성되도록 한다. 사용자를 위해 연다 — Linux는 `xdg-open <path>`, macOS는 `open <path>`, Windows는 `start <path>` — 절대 경로를 알려준다.

리포트는 레이아웃과 스타일링을 위해 **CDN의 Tailwind**, 구조가 그래프 형태일 때 다이어그램을 위해 **CDN의 Mermaid**를 사용한다. Mermaid와 직접 만든 CSS/SVG 비주얼을 혼합한다 — 관계가 그래프 형태(콜 그래프, 의존성, 시퀀스)일 때 Mermaid, 더 편집적인 것(질량 다이어그램, 단면, 접기 애니메이션)을 원할 때 직접 만든 div/SVG. 각 후보는 **before/after 시각화**를 가진다. 시각적으로 표현한다.

각 후보에 대해 다음을 포함한 카드를 렌더링한다:

- **Files** — 관련된 파일/모듈
- **Problem** — 현재 아키텍처가 마찰을 일으키는 이유
- **Solution** — 무엇이 바뀔지 평이한 설명
- **Benefits** — locality와 leverage의 관점으로 설명, 테스트가 어떻게 개선되는지
- **Before / After 다이어그램** — 나란히, 직접 그린, 얕음과 심화를 보여주는
- **추천 강도** — `Strong`, `Worth exploring`, `Speculative` 중 하나, 배지로 렌더링

리포트 끝에 **Top recommendation** 섹션: 어떤 후보를 먼저 다룰지, 그 이유.

**도메인에는 CONTEXT.md 어휘를, 아키텍처에는 `/codebase-design` 어휘를 사용한다.** `CONTEXT.md`가 "Order"를 정의하면 "the Order intake module"로 이야기한다 — "the FooBarHandler"도, "the Order service"도 아니다.

**ADR 충돌**: 후보가 기존 ADR과 모순되면, 마찰이 ADR을 재검토할 만큼 실제로 클 때만 표면화한다. 카드에 명확히 표시한다 (예: 경고 콜아웃: _"ADR-0007과 모순됨 — 하지만 재검토할 가치가 있는 이유는…"_). ADR이 금지하는 모든 이론적 리팩터링을 나열하지 않는다.

전체 HTML 스캐폴드, 다이어그램 패턴, 스타일링 가이드는 [HTML-REPORT.md](HTML-REPORT.md) 참고.

인터페이스는 아직 제안하지 않는다. 파일을 작성한 후 사용자에게 묻는다: "어떤 것을 탐색하고 싶으신가요?"

### 3. 그릴링 루프

사용자가 후보를 선택하면 `/grilling` 스킬을 실행해 설계 트리를 함께 탐색한다 — 제약, 의존성, 심화된 모듈의 형태, seam 뒤에 있는 것, 살아남는 테스트.

결정이 구체화되면서 사이드이펙트가 인라인으로 발생한다 — `/domain-modeling` 스킬을 실행해 진행 중에 도메인 모델을 최신 상태로 유지한다:

- **`CONTEXT.md`에 없는 개념으로 심화된 모듈을 명명하는 경우** `CONTEXT.md`에 용어를 추가한다. 파일이 없으면 게으르게 생성한다.
- **대화 중 모호한 용어를 정제하는 경우** 그 자리에서 바로 `CONTEXT.md`를 업데이트한다.
- **사용자가 핵심 이유로 후보를 거부하는 경우** ADR을 제안한다: _"이것을 ADR로 기록해서 미래의 아키텍처 리뷰가 같은 것을 다시 제안하지 않도록 할까요?"_ 미래 탐색자가 같은 것을 다시 제안하지 않으려면 실제로 필요한 이유일 때만 제안한다 — 일시적인 이유("지금은 그럴 가치가 없다")나 자명한 이유는 건너뛴다.
- **심화된 모듈에 대한 대안 인터페이스를 탐색하고 싶은 경우** `/codebase-design` 스킬을 실행하고 design-it-twice 병렬 서브에이전트 패턴을 사용한다.
