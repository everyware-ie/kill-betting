# FRD-구현 정합성 최신화

FRD와 실제 구현·논의가 어긋난 것으로 **확정된 뒤** 실행한다. 이 스킬은 감지 도구가 아니라 **반영(reconcile) 도구**다 — 감지·안내는 CLAUDE.md "스펙-구현 정합성" 지침이 상시 수행하고, 사용자가 어긋남을 확정하면 이 스킬로 문서를 최신화한다.

> 배경: [2026-07-28 결정 — 정합성 체크는 훅이 아니라 스킬로](../../../docs/ops/governance-gaps-2026-07-28.md). 반복된 drift 사고(임계값 1h↔3h, 편집범위 WAITING↔진행중)는 모두 **git 밖 채널(카톡 등)에서 결정이 바뀌었는데 문서에 반영되지 않은 것**이 원인이었다.

## 언제 사용하나

- AI가 "스펙-구현 정합성" 지침에 따라 불일치를 안내했고, **사용자가 "구현/새 결정이 맞다"고 확정**했을 때
- 카톡 등 채널 밖에서 스펙과 다른 결정이 내려진 사실을 뒤늦게 문서에 남길 때

**감지만 된 상태(사용자 미확정)에서는 실행하지 않는다.** 어느 쪽이 맞는지 확정하는 건 사용자 몫이다.

## 진행 순서

### 1. 대상 FRD 식별

대화 맥락과 이 브랜치의 구현 노트(`docs/product/features/*.md`)의 `FRD:` 링크에서 대상 FRD를 찾는다. 후보가 여럿이면 사용자에게 확인받는다. FRD 파일이 `docs/specs/frd/`에 실재하는지 먼저 확인한다.

### 2. 불일치 항목 수집

무엇이 무엇으로 바뀌었는지 정리한다. 각 항목마다:

- **FRD 원래 값/규칙** (수치·상태조건·enum·API계약 등)
- **확정된 새 값/규칙**
- **출처** — git 밖 채널(카톡 등)이면 그 사실을 명기한다. 근거 검증(SQL 등)이 필요했는데 안 됐다면 그것도 적는다.

특정 코드 경로·스니펫은 넣지 않는다(금방 구식이 된다). 값·규칙·계약 수준으로만 기술한다.

### 3. FRD 갱신 — "개정 (YYYY-MM-DD)" append

FRD 원문을 덮어쓰지 않는다. 파일 하단에 개정 섹션을 **추가**한다. 기존 개정이 있으면 `#2`처럼 번호를 잇는다.

```markdown
## 개정 (YYYY-MM-DD)

<해당 조항 식별(예: S1, S5)>: <한 줄 요약>

- 원래: <FRD 원래 값/규칙>
- 확정: <새 값/규칙>
- 사유·출처: <채널 밖 논의였으면 명기 / 검증 미실시면 명기>
- 관련: [decision](../../decisions/<파일>.md#개정-...), 구현 [PR/이슈]
```

프론트매터 `updated:`를 오늘 날짜로 갱신한다. status가 `approved`면 그대로 둔다(개정은 append이지 재승인 대상 아님).

### 4. docs/decisions/ 기록

- **기존 결정의 값이 바뀐 경우**: 해당 decision 파일에 같은 형식으로 `## 개정 (YYYY-MM-DD)` append. (선례: [2026-07-22-session-settings-and-lifecycle.md](../../../docs/decisions/2026-07-22-session-settings-and-lifecycle.md)의 개정 #1·#2)
- **새로운 결정인 경우**: `docs/decisions/<날짜>-<제목>.md` 새로 작성하고 `docs/decisions/index.md`에 한 줄 추가.

교훈이 있으면 한 줄 남긴다("채널 밖 논의는 최소 한 줄이라도 decisions에 남긴다" 등) — 같은 재발을 줄인다.

### 5. 구현 노트 갱신

이 브랜치 구현 노트(`docs/product/features/<기능>.md`)가 있으면:

- **`## FRD 핵심 값` 표**의 해당 행을 새 값으로 갱신하고 "일치?"를 ✅로.
- **`## 어긋남 기록`**에 날짜·내용·이번 개정 링크를 남긴다.

### 6. 요약 제시 후 확정

바꾼 파일 목록과 각 개정의 before→after를 요약해 사용자에게 보여준다. 사용자 확정 후 종료한다. 커밋·PR은 사용자가 지시할 때만.

## 하지 않는 것

- 요구사항 재정의(다시 캐묻기) — 어느 쪽이 맞는지는 이미 정해졌고, 확정된 것을 옮기기만 한다.
- 어느 쪽이 맞는지 판단 — 그건 사용자가 이미 확정했다.
- 코드 수정 — 문서 최신화만. 구현이 FRD를 따라가야 한다면 별도 작업(이슈)으로 분리.
- 훅 추가·강제 차단 — 팀 결정상 이 흐름은 스킬(안내+반영)로 간다.
