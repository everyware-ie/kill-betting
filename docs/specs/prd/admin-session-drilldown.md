# PRD: 어드민 세션 드릴다운 (Admin Session Drilldown)

- 담당자: jminkkk
- 상태: ready-for-agent
- 관련 ADR: `0001-admin-metrics-access-and-aggregation.md` (접근 방식 재사용), 상세는 도메인 조회 서비스 재사용 결정 추가

---

## 문제 정의

어드민 운영 지표 대시보드는 집계 총량(총 세션 수, 상태별 세션 수 등)만 보여준다.
운영자가 운영 중 "이 세션은 왜 이런 상태지?"를 진단하거나 개별 세션의 현황을 파악하려 해도,
어드민 화면에서는 **개별 Session을 들여다볼 방법이 없다**.

호스트용 세션 조회 화면이 있으나 이는 본인이 참여/생성한 세션에 한정되며,
운영자가 전체 세션을 임의로 조회하는 용도가 아니다.

## 해결책

어드민이 **전체 Session을 목록으로 훑고, 개별 Session의 상세를 드릴다운**해서 볼 수 있게 한다.

- 어드민 세션 목록: 전체 Session을 최근순 페이징으로 나열하고 상태(WAITING/IN_PROGRESS/ENDED)로 필터한다.
- 어드민 세션 상세: 목록에서 한 Session을 선택하면 세션 메타·참가자(Team/TeamMember)·매치별 결과(MatchResult)·스코어보드(ScoreBoard)를 한 화면에서 본다.

모두 **읽기 전용**이며, 기존 어드민 접근 제어(`ADMIN_EMAIL` 화이트리스트)를 그대로 적용받는다.
상세에 필요한 데이터는 이미 도메인에 존재하는 조회 로직(스코어보드·매치 히스토리·참가자)을 **재사용**한다.

## 사용자 스토리

1. 운영자로서, 나는 전체 Session 목록을 최근순으로 보고 싶다, 그래야 서비스에서 어떤 세션들이 열렸는지 훑을 수 있기 때문이다.
2. 운영자로서, 나는 세션 목록을 상태(대기/진행 중/종료)로 필터하고 싶다, 그래야 특정 상태의 세션만 골라 볼 수 있기 때문이다.
3. 운영자로서, 나는 세션 목록을 페이지 단위로 넘기고 싶다, 그래야 세션이 많아도 부담 없이 탐색할 수 있기 때문이다.
4. 운영자로서, 나는 목록의 각 항목에서 세션 이름·호스트·상태·방코드·생성 시각·참가자 수를 보고 싶다, 그래야 상세로 들어가기 전에 세션을 식별할 수 있기 때문이다.
5. 운영자로서, 나는 목록에서 한 Session을 선택해 상세로 진입하고 싶다, 그래야 특정 세션을 깊이 들여다볼 수 있기 때문이다.
6. 운영자로서, 나는 세션 상세에서 세션 메타 정보(이름·호스트·상태·방코드·생성 시각·목표 킬·제한 시간 등)를 보고 싶다, 그래야 세션의 기본 설정을 파악할 수 있기 때문이다.
7. 운영자로서, 나는 세션 상세에서 참가자(Team과 TeamMember) 구성을 보고 싶다, 그래야 누가 어떤 팀으로 참여했는지 알 수 있기 때문이다.
8. 운영자로서, 나는 세션 상세에서 매치별 결과(판별 순위·킬 등 MatchResult)를 보고 싶다, 그래야 각 판이 어떻게 진행됐는지 진단할 수 있기 때문이다.
9. 운영자로서, 나는 세션 상세에서 스코어보드(참가자별 누적 총점)를 보고 싶다, 그래야 최종 집계 결과를 확인할 수 있기 때문이다.
10. 운영자로서, 나는 화이트리스트 밖 사용자로는 세션 목록·상세에 접근할 수 없기를 원한다, 그래야 운영 데이터가 보호되기 때문이다.
11. 운영자로서, 나는 존재하지 않는 세션 ID로 상세를 요청하면 명확한 오류를 받고 싶다, 그래야 잘못된 접근을 인지할 수 있기 때문이다.

## 구현 결정사항

- **모듈 배치**: 신규 `AdminSessionService`를 `domain/admin`에 두고 **조합만** 담당한다. 지표 대시보드(`AdminMetricsService`)와 동일한 원칙 — 집계/조회는 각 소유 도메인에 두고 admin은 오케스트레이션만 한다.
- **어드민 접근 제어**: 신규 접근 제어를 만들지 않는다. `/api/admin/**`에 이미 적용된 `AdminAccessManager`(이메일 화이트리스트)가 신규 엔드포인트도 자동 보호한다.
- **도메인 조회 재사용**: 상세 데이터는 기존 도메인 조회 서비스를 재사용한다. 스코어보드·매치 히스토리 조회는 `sessionId`만 받고 호스트 소유권을 검증하지 않으므로 어드민이 임의 세션을 조회하는 데 그대로 사용할 수 있다. 참가자/팀 조회도 동일하게 재사용한다. **중복 집계 로직을 새로 만들지 않는다.**
- **세션 목록 쿼리(소유 도메인)**: 전체 Session을 페이징 + 상태 필터로 조회하는 쿼리는 `session` 도메인의 repository에 둔다. 상태 필터는 선택적이며, 없으면 전체를 최근 생성순으로 반환한다. 목록 항목의 참가자 수는 세션당 참가자 집계를 활용한다.
- **API 계약**:
  - `GET /api/admin/sessions?status={optional}&page&size` → 페이징된 어드민 세션 요약 목록. 항목: 세션 id·이름·호스트·상태·방코드·생성 시각·참가자 수. 기본 정렬은 생성 시각 내림차순. 페이징 기본값을 서버에서 지정한다.
  - `GET /api/admin/sessions/{sessionId}` → 어드민 세션 상세. 세션 메타 + 참가자/팀 + 매치별 결과 + 스코어보드를 조합한 단일 응답. 존재하지 않는 세션은 404(도메인 예외 규약을 따른다).
  - 공통 응답 래퍼 `ApiResponse` 규약을 따른다. 상세 응답은 재사용하는 도메인 조회 응답 DTO를 필드로 포함하거나 어드민 상세 DTO로 감싼다.
- **DTO**: 목록용 `AdminSessionSummaryResponse`(요약)와 상세용 `AdminSessionDetailResponse`(조합)를 신규로 둔다. 상세는 기존 스코어보드/매치 히스토리/참가자 응답 DTO를 재사용해 구성한다.
- **읽기 전용**: 데이터 생성/수정/삭제·상태 변경 API는 만들지 않는다. 어드민은 조회만 한다.
- **프론트엔드**: 어드민 세션 목록 페이지(상태 필터·페이징) → 세션 상세 페이지 2개 화면을 추가한다. 기존 어드민 화면과 동일하게 인라인 스타일 + `--kn-*` CSS 변수를 사용한다(프로젝트에 Tailwind 미설치). `lib/admin-api.js`에 목록/상세 함수를 추가하고 `USE_MOCK` 분기를 함께 작성한다. 응답은 `{ success, data }` 포맷. 403 시 접근 거부 UI를 재사용한다.

## 테스트 결정사항

- **좋은 테스트**: 구현 세부(재사용하는 서비스 호출 방식, 내부 필드)가 아니라 외부 동작을 검증한다. 즉 "주어진 세션 상태에서 목록이 상태 필터·페이징대로 반환되는가", "상세가 메타·참가자·매치결과·스코어보드를 조합해 반환하는가", "없는 세션은 오류인가"를 검증한다.
- **가장 높은 seam(주력)**: `AdminSessionService` 단위 테스트. 재사용하는 도메인 조회 서비스와 세션 목록 repository를 Mock으로 주입하고, 목록 필터/조합/미존재 처리 로직을 검증한다.
  - 선례: `AdminMetricsServiceTest`(`@ExtendWith(MockitoExtension.class)`, BDDMockito, 조합만 검증).
- **세션 목록 쿼리**: `session` repository의 페이징 + 상태 필터 쿼리는 `@DataJpaTest`로 대표 케이스만 검증(상태 필터 적용 여부, 정렬, 페이지 크기 경계).
  - 선례: `SessionRepositoryTest`, `SessionUserRepositoryTest`.
- **접근 제어**: `/api/admin/**`가 화이트리스트로 이미 보호되므로 별도 통합 테스트는 추가하지 않는다(기존 `AdminAccessManagerTest`로 커버).
- 테스트 메서드명은 한국어 `[상황]_[기대결과]` 형식.

## 범위 외

- 시계열 차트, 리텐션 코호트 매트릭스 (지표 대시보드 범위이자 그 범위에서도 제외됨).
- 데이터 조작: 세션/참가자/매치 결과의 생성·수정·삭제, 세션 상태 강제 변경, 점수 보정.
- 실시간(WebSocket) 반영 — 상세는 조회 시점 스냅샷이다.
- 어드민용 검색(방코드·세션명·호스트 검색). 이번엔 상태 필터 + 페이징까지만. (필요 시 후속 이슈)
- role 기반 권한 체계 (기존과 동일하게 이메일 화이트리스트 유지).
