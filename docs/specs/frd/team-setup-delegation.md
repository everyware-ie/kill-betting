# 팀 구성 권한 위임 & 닉네임 즐겨찾기 — 기능정의서 (FRD)

> 상위: [session.md](session.md)(기존 승인 FRD, B3 규칙 개정 대상), [2026-07-22 결정](../../decisions/2026-07-22-team-setup-delegation.md). status: `approved`(2026-07-25 승격) — 구현 근거로 유효하다.
> 출처: [2026-07-22 회의 종합](../../meetings/2026-07-22/synthesis.md) — 사용자 인터뷰 항목 3, 4.
> **담당: phs00**

## 1. 개요

현재 팀 구성(팀 생성/플레이어 추가·수정·삭제/리더 지정)은 전부 Host만 가능하다([session.md B3](session.md)). 인터뷰에서 방장이 모든 팀원 등록을 혼자 처리해야 해서 힘들다는 피드백을 받았다. 이 FRD는 ① 팀 리더에게 자기 팀 팀원 관리 권한을 위임하고 ② 자주 쓰는 닉네임을 즐겨찾기로 저장하는 기능을 다룬다.

## 2. 사용자 플로우

1. Host가 팀을 생성하고 리더를 지정하는 것까지는 기존과 동일(Host 전용 유지)
2. **리더로 지정된 사용자**는 이제 본인 팀에 한해 팀원(닉네임) 추가·수정·삭제 가능
3. 팀원 추가 시, 자주 쓰는 닉네임이 있으면 **즐겨찾기 목록에서 선택**해 바로 추가(타이핑 불필요)
4. 즐겨찾기에 없더라도 **최근 함께한 닉네임**이 함께 노출되어, 거기서 바로 추가하거나 **즐겨찾기로 등록**할 수 있다
5. 새 닉네임을 직접 입력하면 "즐겨찾기에 추가" 옵션 제공

## 3. 화면/인터랙션 정의

| 화면 ID | 변경 사항 |
|---|---|
| room/[id]/setup | 팀 리더에게도 "팀원 추가/수정/삭제" UI 노출(기존엔 Host에게만 보임). 닉네임 입력란 옆에 **즐겨찾기 + 최근 함께한 닉네임** 선택 UI 추가 — 각 항목에서 바로 추가, 최근 항목은 즐겨찾기 등록 가능 |
| mypage | 즐겨찾기 닉네임 목록 관리(추가/삭제) — 마이페이지 내 섹션으로 배치 |

## 4. 기능 규칙 (Business Rules)

| # | 규칙 | 근거 |
|---|---|---|
| T1 | **팀 리더는 본인이 리더인 팀에 한해** 플레이어(닉네임) 추가·수정·삭제 가능 | [2026-07-22 결정](../../decisions/2026-07-22-team-setup-delegation.md) — [session.md B3](session.md) 개정 |
| T2 | **Host는 기존처럼 모든 팀**에 대해 추가·수정·삭제·리더 지정 가능 (상위 권한 유지, 리더 권한을 대체하지 않고 포함) | 동일 |
| T3 | **팀 생성·리더 지정·리더 해제는 Host 전용으로 유지** — 팀 구조 자체를 바꾸는 조작은 위임하지 않음 | 회의에서 명시적으로 범위 제한 |
| T4 | 팀당 최대 4명 유지. 닉네임 고유 범위는 **팀 내 → 세션 내**로 확대(2026-07-28 결정, `[구현 반영 예정]`) — 같은 세션의 다른 팀에 동일 닉네임 등록 금지 | [session.md B5](session.md) — 세션 내 고유 확대는 [2026-07-22 결정 개정](../../decisions/2026-07-22-team-setup-delegation.md#개정-2026-07-28) |
| T5 | 닉네임 즐겨찾기는 **사용자(User) 단위로 저장**되며, 세션에 종속되지 않아 다음 세션에서도 재사용 가능 | 신규 |
| T6 | 즐겨찾기에서 선택해 추가해도 T1·T4의 검증(권한·최대인원·중복닉네임)은 동일하게 적용 | 기존 `addPlayer` 검증 로직 재사용 |
| T7 | **최근 함께한 닉네임**: 내가 리더로서 최근 세션에서 팀에 등록했던 닉네임 중 **즐겨찾기에 없는 것 최대 10개**를 함께 제공한다. 저장 대상이 아니라 조회 시 계산되는 파생 데이터 | 신규 — 인터뷰 항목 4(반복 입력 번거로움)의 연장 |
| T8 | 즐겨찾기는 **사용자당 최대 20개**. 초과 시 추가를 거부한다 | 신규 — §5 미결 해소 |

## 5. 예외 처리

| 상황 | 처리 |
|---|---|
| 리더가 아닌 팀원이 팀 구성 시도 | 403 |
| 리더가 **다른 팀**의 팀원을 추가/수정/삭제 시도 | 403 (본인 팀만 가능) |
| 리더가 팀 생성·리더 지정 시도 | 403 (Host 전용 유지) |
| 즐겨찾기 20개 초과 등록 시도 | 400 (상한 안내) |
| 세션 내 다른 팀에 이미 등록된 닉네임으로 추가 시도 | 400 — 현재는 팀 단위로만 검증됨, `[구현 반영 예정]`(2026-07-28 결정, T4 참고) |

## 6. 데이터

- `TeamConfigureService`의 권한 검증을 `validateHost` 단일 검증에서 **`validateHostOrOwnTeamLeader(session, team, userId)`** 형태로 확장(팀 생성/리더 지정은 `validateHost` 유지)
- 신규 엔티티: `FavoriteNickname`(또는 유사) — user, nickname, createdAt. 사용자당 최대 20건(T8)
- 즐겨찾기 조회 응답에 **`recentUnfavorited: List<String>`**(최대 10개) 포함 — 별도 화면·별도 대규모 쿼리 없이 즐겨찾기 조회 시 함께 계산(T7)

## 7. 비기능 요구 / 열린 질문

- **"최근 함께한 닉네임"의 "최근" 기준** — 첫 버전은 **내가 리더였던 최근 세션들에서 등록한 닉네임** 기준으로 확정한다(구현 단순, 쿼리 부담 낮음). 기간 기반(예: 30일) 기준은 필요성이 확인되면 후속 논의
- 리더가 위임받은 권한으로 실수로 팀원을 삭제하는 경우에 대한 되돌리기(undo)는 이번 범위 밖으로 제안(별도 논의)
