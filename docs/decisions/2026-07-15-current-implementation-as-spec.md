# 노션-코드 불일치 해소 — 현재 구현을 최종 스펙으로 채택

## 배경

[PRD review 작업(2026-07-14)](../specs/prd/kill-betting-core.md#8-노션-대조-결과-2026-07-14)에서 노션 기획 원본과 코드 구현 사이의 불일치 2건, 확인 필요 3건을 발견해 "다음 회의 안건"으로 남겨뒀다.

그런데 킬내기는 이미 **운영 서버에 배포되어 지응의 친구 그룹을 통해 실사용 중**이다 — 즉 코드에 구현된 구조가 사실상 팀이 최종적으로 합의·출시한 스펙이고, 노션의 초기 기획은 개발 과정에서 자연스럽게 갱신되지 않은 낡은 계획이다. phs00 확인(2026-07-15): 코드 구조를 최종 결론으로 삼고 스펙 문서를 구현 기준으로 업데이트하되, 원래 계획과 달라진 지점은 히스토리로 남긴다.

## 결정

**현재 코드 구현을 최종 스펙으로 채택한다.** 노션 기획 원본은 초기 설계 의도를 보여주는 히스토리로 [team/archive](https://github.com/everyware-ie/mechuri-docs/tree/main/team/archive/notion-2026-07/)에 그대로 보존하고, PRD/topics 등 살아있는 스펙 문서는 구현 기준으로 갱신한다.

### 항목별 최종 결론

| # | 최초 계획 (노션) | 최종 채택 (구현대로) | 비고 |
|---|---|---|---|
| 1 | 닉네임 중복 허용, 방 안에서 "닉네임#id"로 구분 (FDD) | **닉네임 전역 유일** (`User.nickname` unique) | 닉네임 자체가 사실상 로그인 식별자 역할을 겸함. 친구끼리 닉네임 겹치면 한쪽이 다른 닉네임 사용 필요 — 알려진 제약으로 수용 |
| 2 | 매치 1건 = 전체 팀 결과 포함, 전 팀 제출 후 확정 (유저스토리) | **팀별 독립 Match + 독립 confirm** (`Match.team_id` FK) | 팀마다 각자 스크린샷 업로드→confirm. 다른 팀 제출을 기다릴 필요 없어 실사용상 더 자연스러운 것으로 확인 |
| 3 | PUBG API로 playerId 자동 조회 후 저장 (기획안 §14) | **미구현** — `pubgNickname`/`pubgPlayerId` 필드는 존재하나 수동 입력용, API 연동 없음 | 확장 후보로 보류 |
| 4 | Top10 미달성 페널티 "-2점" 고정, 필수 규칙 (FDD) | `RuleType.SURVIVAL_PENALTY`로 구현, 수치는 세션별 `Rule.value`로 **설정 가능한 값** | "고정 -2"가 아니라 "기본값 -2, 커스터마이징 가능"이 실제 — 오히려 기획안 §9 "규칙 커스터마이징" 원칙과 일치 |
| 5 | (기획 문서에 명시 없음) TeamMessageController | **팀 구성 단계의 실시간 협업 채널** — WebSocket(STOMP)으로 팀 생성/플레이어 추가·수정·삭제/리더 지정을 참가자 전원에게 실시간 브로드캐스트. 채팅 기능 아님 | 이름(TeamMessage)이 오해 소지 있으나 기능 자체는 명확 |

### 확인 완료 (일치)

- 세션 시작 조건: 최소 2팀, 팀마다 리더 배정 필수, 팀마다 최소 1명 이상 플레이어 등록 필수 — FDD "각 팀 최소 1명 로그인 필요, 참여자 닉네임 모두 입력" 정책과 정확히 일치 (`SessionService.startSession`)
- 웹소켓 실시간 스코어보드, 점수조정 사유 필수+host 권한 — 기존 PRD review에서 이미 확인됨

## 사유

- 실사용자가 있는 프로덕션 코드가 문서보다 신뢰도 높은 진실이다. 노션 계획대로 코드를 "고치는" 것은 이미 검증된 실사용 경험을 되돌리는 리스크만 있고 얻는 게 없다.
- 다만 계획과 달라진 이유를 기록해두지 않으면 다음에 이 코드를 보는 사람(팀원이든 AI든)이 "왜 이렇게 짰지"를 다시 추적해야 한다 — 이 결정 문서가 그 히스토리다.
