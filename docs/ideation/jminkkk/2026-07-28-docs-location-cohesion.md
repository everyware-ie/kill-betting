# 논의: 프로젝트 문서의 "집"을 어디에 둘 것인가 — 허브 응집 vs 프로젝트 응집

> 작성: jminkkk / 2026-07-28 / 회의 논의용 개인 정리 (raw, 입장 포함)
> 연결: [governance-gaps-2026-07-28](../../ops/governance-gaps-2026-07-28.md)의 🔴 "admin PRD 위치" 항목 = 같은 문제의 구체 사례.
> 이 노트는 그 안건을 **생명주기 전체**로 확장해 각 방식의 장단을 리스트업한 것.

---

## 1. 문제

같은 프로젝트(킬내기)의 문서가 **repo 2곳**에 갈라져 있다.

- `mechuri-docs`(허브) — `products/kill-betting/`: 아이디어(raw)·회의·결정·FRD/PRD
- `kill-betting`(코드) — `docs/`: 일부 FRD/PRD 원문 + 스텁

증상: 어느 게 정본인지 헷갈리고, 갱신하면 갈라진다. 실제 사고도 이미 발생 — admin PRD 2건이 허브 규칙(스텁만) 신설 전에 코드 repo에 원문으로 남음, 스펙(1h)-구현(3h) 불일치.

**핵심 오해 방지**: 지금 불편은 "repo가 2개여서"가 아니라 **"정본이 안 정해져서"**다. 정본 단일화는 어느 방식이든 지켜야 하는 전제. 이 문서는 그 정본을 *어느 repo에* 둘지를 다룬다.

---

## 2. 두 가지 방식

| | **방식 H — 허브 응집 (현행 CLAUDE.md)** | **방식 P — 프로젝트 응집** |
|---|---|---|
| FRD/PRD 정본 | 허브 `products/<제품>/specs/` | 코드 repo `docs/` |
| 코드 repo | 링크 + 구현 노트 스텁만 | 문서 원본 보유 |
| 허브 역할 | 전 제품 기획·결정 통합 파이프라인 | 팀 공통(멤버·컨벤션)만 / 축소 or 폐지 |
| 전제 | 기획은 팀의 산출물, 코드와 분리 | 전원 개발자, 문서=코드의 일부 |

**이번 논의의 촉발점**: phs00 포함 **전원이 개발**한다. 방식 H의 원래 명분("기획자는 코드 repo에 안 들어오니 공용 공간 필요")이 약해졌다 → 방식 P 재검토 여지.

---

## 3. 생명주기별 장단 (기획 → 개발 → 개선)

### 🟦 기획 단계 (아이디어 발산 → 회의 종합 → 결정 → 스펙 초안)

**방식 H**
- 👍 코드 노이즈 없는 사고 공간. raw 발산·회의 종합이 구현 압박과 분리됨
- 👍 여러 제품 넘나드는 아이디어·결정을 한 곳에서 교차 관리
- 👍 아직 코드가 없는 초기 아이디어도 자연스럽게 들어감
- 👎 기획하려고 별도 repo를 열어야 함 (컨텍스트 스위칭)
- 👎 현재 구현 상태와 분리돼, 스펙이 코드 현실과 겉돌 위험

**방식 P**
- 👍 기획 시점부터 코드 맥락(현 구현·이슈·PR)이 바로 옆 → 현실적 스펙
- 👍 전원 개발자면 어차피 코드 repo에 상주 → 스위칭 없음
- 👎 코드 repo git 히스토리에 기획 발산 churn이 섞임
- 👎 코드 없는 초기 아이디어를 코드 repo에 두는 어색함
- 👎 제품이 여러 개면 아이디어가 repo마다 흩어짐

### 🟩 개발 단계 (구현 착수 → PR → 머지)

**방식 H**
- 👍 approved FRD가 유일 진실, 스텁+링크로 근거 명확
- 👎 구현하며 스펙 보려면 repo 왕복
- 👎 스펙-구현 동기화가 사람 규율에 의존 → **실제로 깨짐**(1h vs 3h, git 밖 카톡 논의 미반영)
- 👎 코드 repo 스텁의 링크 버전이 허브 개정을 못 따라감 (작업6 sync check를 수동으로 돌려야)

**방식 P**
- 👍 스펙과 코드가 **같은 repo·같은 PR**에서 움직임 → 스펙 변경과 구현 변경을 한 diff로 리뷰
- 👍 "PR의 FRD 수치 vs 구현 diff 자동 대조" 같은 훅이 한 repo라 구현 쉬움 → 1h/3h류 불일치 잡기 유리
- 👍 FRD 승인 게이트(#102/#103)도 이미 코드 repo 훅으로 만들어짐 — P와 자연히 정합
- 👎 문서 status(draft/review/approved) 규율을 코드 repo에서도 동일하게 지켜야 함. 안 지키면 도로 흩어짐

### 🟨 개선 단계 (운영 → 개정 → deprecated)

**방식 H**
- 👍 결정 개정 이력(append 방식)이 팀 결정 아카이브로 축적
- 👍 제품 넘나드는 회고·패턴 재사용
- 👎 코드 개선 PR과 FRD 개정이 다른 repo → 동기화 갭 재발, deprecated 이중 관리

**방식 P**
- 👍 기능 개선 시 코드 + FRD를 **한 PR/한 이슈**로 함께 개정 → 어긋남 최소
- 👍 "이 기능 왜 이렇게 됐나"를 한 repo git blame으로 추적
- 👎 팀 차원 결정(프로세스·표준)·제품 무관 회고는 코드 repo에 둘 자리가 애매
- 👎 제품이 늘면 공통 결정이 특정 코드 repo에 갇힘

---

## 4. 한 줄 트레이드오프 요약

- **방식 H**는 *기획·결정의 통합*과 *제품 확장성*에 강하고, *개발·개선 단계의 스펙-구현 동기화*에 약하다 (실제로 여기서 사고가 남).
- **방식 P**는 *개발·개선 단계의 스펙-구현 정합*에 강하고(한 repo·한 PR), *제품 확장*과 *코드 없는 초기 기획*에 약하다.

## 5. 내 입장 (jminkkk)

**현 상황(제품 1개 = 킬내기, 전원 개발)에선 방식 P가 실용적이라고 본다.**

근거:
1. 방식 H의 원래 명분(기획자 비개발)이 사라졌다 — phs00도 개발함
2. 실제 터진 사고(1h/3h 불일치, admin PRD 방치)는 전부 **repo가 갈려서 동기화가 사람 규율에 의존**해 생김. 한 repo면 PR diff·훅으로 구조적으로 막을 수 있다
3. FRD 승인 게이트 훅(#102/#103)이 이미 코드 repo에 있다 → P와 정합
4. 제품 확장은 아직 없음(YAGNI). 늘어나면 그때 허브를 재도입하면 됨

**단, 조건부.** 방식 P로 가도 흩어짐을 막으려면 아래 3규율은 그대로 가져가야 한다 (repo 위치 무관):
- **정본 하나** — FRD는 `docs/specs/frd/`에만. README·주석에 스펙 복붙 금지
- **status 관리** — draft → review → approved, approved만 구현 근거 (#102/#103 훅으로 강제)
- **raw 불변** — 발산 메모는 고쳐쓰지 않고 새 노트로 보완

## 6. 방식 P 채택 시 파급 (미리 봐둘 것)

- CLAUDE.md·docs 컨벤션 개정: "features/는 허브 approved FRD 스텁만" 규칙을 뒤집거나 "레포별 예외"로
- 허브 `products/kill-betting/` 이관: FRD/PRD/decisions/raw를 코드 repo `docs/`로

- 진행 중 작업 충돌 주의: 지금 A·C·D그룹 PR 다수 열려 있음 → 이관은 PR 큐 정리 후
