# 팀 워크플로우

> 이슈 생성부터 머지까지의 흐름과 기획 논의 규칙을 정의한다.
> 변경 시 팀 합의 후 이 파일을 업데이트한다.

---

## 기획 논의 규칙

### 시간 제한
- 논의 시작 전 **주제와 우선순위를 먼저 확정**한다
- 주제별 최대 **15분** 논의 후 결정
- 결론이 안 나면 영업중 방식 적용:
  1. 초반 투표 → 15분 논의 → 최종 투표

### MVP 정의 기준
- "이게 없으면 배포 못 한다" 기준으로만 MVP에 포함
- 확신이 없으면 **일단 만들고 써보면서 검증** (프로토타입 우선)
- 기능 정의는 반드시 FRD 템플릿으로 문서화 → [`docs/product/features/_template.md`](_template.md) 참고

## 개발 워크플로우

```
이슈 생성 → 브랜치 생성 → 구현 → PR → 머지
```

### 1. 이슈 생성
- AI와 함께 이슈 먼저 작성 후 구현 시작
- 이슈에 **담당자 명시** (AI 중복 작업 방지)
- 요구사항 변경 시 → 기존 이슈 업데이트 또는 새 이슈 생성 후 팀 공유

### 2. 브랜치 생성
- 브랜치 네이밍: `<작업자>/<타입>/<기능>` → [`conventions/git.md`](../../.claude/conventions/git.md) 참고
- 이슈 번호를 브랜치 이름에 포함하는 것을 권장

### 3. 구현
- 컨벤션 준수: 백엔드 → [`docs/backend/conventions.md`](../backend/conventions.md), 프론트 → [`docs/frontend/conventions.md`](../frontend/conventions.md)
- 도메인 용어 확인: [`domain/glossary.md`](../../.claude/domain/glossary.md)

### 4. PR
- PR 제목: 커밋 메시지 형식과 동일 (`type(scope): 설명`)
- PR 본문 필수 항목:
  - 변경 이유
  - 테스트 방법
  - 관련 이슈 번호

### 5. 머지
- `feature/*` → `develop`: PR 필수
- `develop` → `main`: PR 필수 + approval 후 머지

## 요구사항 변경 프로세스

변경 발생 시 아래 순서로 처리한다.

1. 변경 내용을 이슈로 먼저 등록
2. 관련 FRD 파일 업데이트 (`docs/product/features/`)
3. 팀 공유 후 구현 시작

> 구현 먼저 하고 문서는 나중에 → 팀원이 동일한 내용을 인지하지 못하는 원인

## 이슈 소유권 (AI 충돌 방지)

누구나 모든 영역을 작업할 수 있다. 단, **작업 시작 전 이슈에 본인을 assign**한다.

### 규칙
- 이슈 assign 없이 구현 시작 금지
- 같은 이슈에 두 명이 동시에 작업하지 않는다
- AI로 작업할 때도 동일하게 적용 — 이슈 번호를 AI 컨텍스트에 명시한다

### AI 활용 시 컨텍스트 예시
```
이슈 #42 담당. session 도메인의 점수 계산 로직 구현 중.
다른 팀원이 같은 도메인을 건드리지 않도록 이슈 assign 확인 후 시작.
```

> assign된 이슈가 없으면 작업 범위가 겹칠 수 있으니 반드시 확인할 것
