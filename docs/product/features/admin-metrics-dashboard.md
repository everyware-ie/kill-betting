# PRD: 운영 지표 어드민 대시보드 (Admin Metrics Dashboard)

- 담당자: jminkkk
- 상태: ready-for-agent
- 관련 ADR: (신규) 어드민 접근 방식 + 지표 집계 방식

---

## 문제 정의

개발자와 서비스 운영자(기획자 포함)가 서비스가 실제로 어떻게 쓰이는지 —
가입은 늘고 있는지, 유저가 세션에 얼마나 참여하는지, 재방문(리텐션)은 어떤지 —
한눈에 확인할 수단이 없다. 지금은 DB를 직접 열어봐야만 알 수 있어,
운영 판단과 기획 검토에 필요한 지표를 즉시 볼 수 없다.

(에러/인프라 모니터링은 별도 서버가 담당하므로 이 문제의 범위가 아니다.)

## 해결책

지정된 운영자만 접근 가능한 읽기 전용 지표 대시보드(`/admin`)를 제공한다.
접속하면 성장·참여·활성·리텐션 지표가 현재 DB 값 기준으로 카드 형태로 렌더링된다.
데이터를 나열하는 것이 아니라, 서비스 판단에 도움이 되는 집계 지표를 노출한다.

## 사용자 스토리

1. 운영자로서, 나는 `/admin`에 접속했을 때 화이트리스트에 등록된 이메일 계정이면 대시보드를 볼 수 있기를 원한다, 그래야 허가된 사람만 운영 데이터를 확인할 수 있기 때문이다.
2. 화이트리스트에 없는 유저로서, 나는 `/admin` 접근이 거부(403)되기를 원한다, 그래야 일반 유저에게 운영 데이터가 노출되지 않기 때문이다.
3. 운영자로서, 나는 총 가입 유저 수를 보고 싶다, 그래야 서비스 전체 규모를 파악할 수 있기 때문이다.
4. 운영자로서, 나는 최근 7일/30일 신규 가입 수를 보고 싶다, 그래야 최근 성장 추세를 알 수 있기 때문이다.
5. 운영자로서, 나는 총 세션 수와 상태별(진행 중/종료) 세션 수를 보고 싶다, 그래야 서비스 활동량을 파악할 수 있기 때문이다.
6. 운영자로서, 나는 세션당 평균 참가자 수를 보고 싶다, 그래야 세션이 얼마나 큰 규모로 열리는지 알 수 있기 때문이다.
7. 운영자로서, 나는 유저당 평균 참여 세션 수를 보고 싶다, 그래야 유저들이 얼마나 반복적으로 참여하는지 알 수 있기 때문이다.
8. 운영자로서, 나는 최근 7일/30일 활성 유저 수(해당 기간에 세션에 참여한 유저)를 보고 싶다, 그래야 실사용자 규모를 알 수 있기 때문이다.
9. 운영자로서, 나는 W1 간이 리텐션(가입 후 7일 내 세션에 1회 이상 참여한 유저 비율)을 보고 싶다, 그래야 신규 유저가 서비스에 자리 잡는지 판단할 수 있기 때문이다.
10. 운영자로서, 나는 이 대시보드가 읽기 전용이기를 원한다, 그래야 지표를 확인하다 실수로 운영 데이터를 바꾸지 않기 때문이다.

## 구현 결정사항

### 접근 제어
- 인증은 기존 JWT를 그대로 사용한다. 어드민 여부는 **role 필드가 아니라 이메일 화이트리스트**로 판단한다.
  - 사유: 운영자는 소수 고정 인원이고, User에 role 개념이 없다. role 도입(엔티티/마이그레이션)은 이 규모에 과하다. 인원이 늘면 role 체계로 승격한다. (ADR로 기록)
- `ADMIN_EMAILS` 환경변수로 화이트리스트를 주입한다.
- `SecurityConfig`에 `/api/admin/**` 접근 규칙을 추가한다. 인증된 유저 중 이메일이 화이트리스트에 있을 때만 통과, 아니면 403.
- 화이트리스트 판정은 `common/security`의 별도 컴포넌트(AuthorizationManager 성격)로 분리한다.

### 백엔드 모듈
- 신규 `domain/admin` 모듈을 만든다. 읽기 전용 오케스트레이션만 담당한다.
  - 인터페이스: `GET /api/admin/metrics` → 지표 묶음 응답(`AdminMetricsResponse`, record).
  - `AdminMetricsService`는 각 도메인의 집계 조회 결과를 **조합**해 응답을 만든다. 자체적으로 타 도메인 엔티티/테이블을 직접 조회하지 않는다.
- **집계 쿼리는 각 지표의 소유 도메인에 둔다** (모듈 경계/ArchUnit 준수):
  - 가입 수, 기간별 신규 가입 수 → `user` 도메인 (`User.createdAt` 기준 count)
  - 세션 수/상태별 세션 수 → `session` 도메인 (`Session.status`)
  - 세션당 평균 참가자, 유저당 평균 참여 세션, 기간별 활성 유저, W1 리텐션 → `session` 도메인 (`SessionUser` 기반; SessionUser는 이미 User를 참조하므로 join 가능)
- 지표는 **조회 시점에 집계**한다. 별도 분석 저장소/배치는 두지 않는다. (ADR로 기록)

### 지표 계산 정의
- 활성 유저(기간 N일): 최근 N일 내 `SessionUser.joinedAt`이 존재하는 distinct user 수.
- 세션당 평균 참가자 수: 전체 `SessionUser`(ACTIVE) 수 / 전체 세션 수. (분모 0이면 0)
- 유저당 평균 참여 세션 수: 전체 `SessionUser` 수 / 전체 유저 수. (분모 0이면 0)
- W1 리텐션: 분모 = 가입 후 7일이 경과한(관측 가능한) 유저 수, 분자 = 그중 `가입일 ~ 가입일+7d` 사이에 `SessionUser.joinedAt` 기록이 1건 이상인 유저 수. 비율(%)로 표기. 분모 0이면 0.
  - 아직 7일이 지나지 않은 신규 유저는 분모에서 제외(관측 미완료).

### API 계약 (초안)
```
GET /api/admin/metrics
200 OK
{
  "totalUsers": number,
  "newUsers7d": number,
  "newUsers30d": number,
  "totalSessions": number,
  "sessionsByStatus": { "IN_PROGRESS": number, "ENDED": number, ... },
  "avgParticipantsPerSession": number,
  "avgSessionsPerUser": number,
  "activeUsers7d": number,
  "activeUsers30d": number,
  "w1RetentionRate": number   // 0~100 (%)
}
403 Forbidden  // 화이트리스트 밖
```
(공통 응답 래퍼 `ApiResponse` 규약을 따른다.)

### 프론트엔드
- `app/admin/page.js` 신규 페이지. 신규 컴포넌트이므로 Tailwind + CSS 변수(`--kn-*`)를 사용한다(인라인 스타일 금지).
- `lib/admin-api.js` 신규. `getMetrics()` 제공하며 `USE_MOCK` 분기를 함께 작성한다. 응답은 `{ success, data }` 포맷.
- 지표를 그룹(성장/참여/활성/리텐션)별 카드로 렌더링한다. 403 응답 시 접근 거부 UI를 노출한다.

### 문서/용어
- `.claude/domain/glossary.md`에 용어 추가: `Admin(어드민)`, `활성 유저(Active User)`, `리텐션(Retention, W1)`.
- ADR 1건 작성: (1) 어드민 접근 = 이메일 화이트리스트, (2) 지표 = 조회 시점 집계(별도 저장소 없음).

## 테스트 결정사항

- **좋은 테스트**: 구현 세부(쿼리 방식, 내부 필드)가 아니라 외부 동작을 검증한다.
  즉 "주어진 데이터 상태에서 계산된 지표 값이 맞는가", "화이트리스트 밖이면 403인가"를 검증한다.
- **가장 높은 seam(단일)**: `AdminMetricsService` 단위 테스트. 각 도메인 집계 조회를 Mock으로 주입하고,
  계산 로직(평균, W1 리텐션 %, 분모 0 방어)을 검증한다.
  - 선례: `domain/session/service/SessionServiceTest`, `domain/team/service/TeamServiceTest` (`@ExtendWith(MockitoExtension.class)`, BDDMockito).
- **접근 제어 seam**: `/api/admin/**` 403 동작은 얇은 슬라이스/통합 테스트로 최소한만 검증한다(화이트리스트 유저 통과 / 비화이트리스트 403).
- 도메인별로 추가한 집계 쿼리는 `@DataJpaTest`로 대표 케이스만 검증(경계값: 분모 0, 기간 경계).
- 테스트 메서드명은 한국어 `[상황]_[기대결과]` 형식.

## 범위 외

- 시계열 추이 **차트/그래프** (v1은 숫자 카드만).
- 전체 리텐션 **코호트 매트릭스**(N주차별). v1은 W1 단일 지표만.
- **세션 단위 드릴다운**(세션 상세/매치 원본/스코어보드 원시 데이터 열람).
- 데이터 **조작/수정** 기능 (읽기 전용).
- role 기반 권한 체계 도입.
- 에러/인프라 **모니터링**(별도 서버 담당).

## 추가 참고사항

- 라이브 화면 내 호스트용 "운영 메뉴"(AdminModal: 점수 조정/세션 종료/룰 수정)와는 **완전히 별개** 기능이다. 이 어드민은 개발자/서비스 운영자 전용이다.
